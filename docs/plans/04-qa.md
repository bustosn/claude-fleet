# 04 — QA runs

A QA run checks a branch or PR for bugs the way a careful reviewer who has never seen the code would: from the ticket, the diff and the code around it, not from the author's summary. Fleet owns the pipeline as server code (like dialogues): it builds the context, starts fresh reviewer chats in parallel, sends every finding to a separate verifier, turns the spec into a test plan, runs the tests it can, and writes one report with a gate. The person signs off on the spec and on anything that writes.

## Why

JL-7507 (tools2 #5163, ETL #7487) went through an author self-review, a "low/medium" code review, a recheck and a two-agent dialogue, and still had ten real bugs that a single fresh chat found in one pass. Each one maps back to a gap in the process:

| Gap | Effect |
|---|---|
| The author reviewed its own work, or reviewers started from the author's summary | Reviewers inherited the author's mental model and confirmed it |
| No written list of states and where each one should appear | Nobody asked "a case marked Do Not Work comes back to 146: which page shows it?" |
| "Low or medium, no nitpicking" was applied to search depth | Shallow reads; severity should filter the report, never the search |
| Each file was reviewed on its own | Bugs that live *between* files (four queries defining "open early loss" four ways) were invisible |
| Tests used fixtures the author wrote | Flat JSON, no IN lists, no bounce-back cases; nothing could surprise the author |
| A dialogue about PR size was counted as a review | Two agents converge and agree; neither was hunting for bugs |
| Rechecks only looked at the latest fix | The whole feature was never reviewed again end to end |
| Open questions were left as questions | A cross-client data leak sat in "for you to decide" instead of being called a bug |
| The PR description was never checked against the code | It said the due date releases the hold; the code never looks at the due date |

The QA run closes each of these by construction, not by asking agents to try harder.

## Principles

1. **The author never reviews.** Reviewer and verifier chats are new chats. They never receive the author chat's messages, summary or reasoning. Their only inputs are the context pack (below), the signed-off state matrix and the lens brief.
2. **Severity filters the report, never the search.** Every lens reads the whole context pack at full depth. The profile (quick / standard / deep) decides how many lenses run and what is shown, not how carefully each one reads.
3. **No finding without a failure scenario.** A finding must say: this state and these inputs, through this code path, give this wrong result. "Could be an issue" or "consider" is not a finding and is dropped.
4. **Every finding is attacked before it is reported.** A separate verifier tries to disprove it against the code. Only CONFIRMED and PLAUSIBLE survive.
5. **Evidence, not assertion.** A test passes when there is a query result, a screenshot or a request log that shows it, attached to the test.
6. **Spec first.** The state matrix and the claims list are written and signed off before the lenses run. Lenses check code against them; tests are generated from them.
7. **Data the author didn't write.** Fixtures are built from real value shapes sampled read-only from prod readers, plus a fixed hostile-input set.
8. **Nothing outward-facing on its own** (overview principle 4). Fleet never comments on a PR, changes a label or writes to Jira by itself. Dev DB writes go through the SQL view's confirm step. Prod is read-only, always.
9. **Escaped bugs make the checklists longer.** Every bug found after a run passed is recorded against the lens that should have caught it, and that lens's checklist grows.

## Concepts

| Term | Meaning |
|---|---|
| Target | A repo plus a head (branch, PR number or worktree) and a base. Several targets can be one run (tools2 + ETL for one ticket). |
| Context pack | Everything a reviewer reads, built by the server, frozen per run. |
| Claims | Testable statements pulled from the ticket and PR description ("the due date releases the hold"). |
| State matrix | Entities × states × transitions × surfaces, with the expected behaviour in each cell. Signed off by the person. |
| Lens | One reviewer focus with its own brief, checklist and output schema. |
| Finding | A structured bug report from a lens. |
| Verdict | A verifier's CONFIRMED / PLAUSIBLE / REJECTED on one finding, with reasoning. |
| Test case | Setup, action, expected result and a check, generated from the matrix, claims and findings. |
| Evidence | Query result, screenshot, network log or console log attached to a test or finding. |
| Gate | The run's ship verdict: blocked, needs decisions, or clear. |
| Profile | quick, standard or deep: which lenses run and how many agents. |

## Pipeline

```
Intake → Context pack → Claims + State matrix (person signs off) → Lenses (parallel)
      → Dedupe → Verify (parallel) → Test plan → Run tests → Report + Gate → Learn
```

Every phase writes to the run's state file, so a run survives a restart and resumes at the phase it was in (like dialogues).

### 0. Intake

- Input: one or more targets, an optional Jira key, a profile.
- Resolve the base as the merge base with the **remote** default branch (`git fetch` first, then `git merge-base origin/<default> HEAD`). A stale local `development` turned a 15-file diff into a 76-file diff during JL-7507; never diff against the local branch.
- Pull the ticket from Jira (read-only, `server/jira.ts`) and the PR title, body, labels and existing review comments with `gh pr view --json`.
- Record the head SHA of every target. If the head moves during a run, the run is marked stale and offers to re-run only the lenses whose files changed.

### 1. Context pack

Built deterministically by the server, not by an agent. Stored under `state/qa/<runId>/pack/`.

| Part | How |
|---|---|
| Diff | `git diff <base>...<head>` per target, with stat |
| Changed files, in full | Every changed file at head (not only the hunks) |
| Base versions | The same files at base, so a lens can see what was removed |
| Callers | For every changed function, method, route name, JS global, SQL table and constant: `git grep` hits outside the diff, with 30 lines around each hit, capped per symbol |
| Shared surfaces | Routes, menus, jobs, cron schedule, webpack/mix entries, Blade includes that reference a changed file |
| Schema | `INFORMATION_SCHEMA` columns and indexes for every table named in the diff, from the dev connection and the prod reader (`fleet_sql`, read-only), with a note when they differ or the table is missing on one side |
| New DDL | Any `.sql` in the diff or listed in the PR body; flagged when a table the code uses exists in no migration and no DDL file |
| Ticket and PR | Jira description and latest comments; PR body |
| Repo rules | Repo `CLAUDE.md` and the user's global `CLAUDE.md` rules that apply (index prefixes, files never to commit) |
| Value samples | Filled in at phase 2 (below) |

Explicitly **not** in the pack: the author chat's transcript, summaries or self-review.

The pack has a size budget. Past it, callers and base versions are trimmed first, never the changed files.

### 2. Claims and state matrix

One fresh **spec agent** reads the pack and drafts both. The person edits and signs off in the UI. Lenses do not start until sign-off (the quick profile can skip sign-off and mark the run "unsigned spec").

**Claims.** Every sentence in the ticket and PR body that promises behaviour becomes a row: claim, source, the code that should make it true (filled in by the conformance lens), and a test id.

**State matrix.** Structure:

- **Entities**: the things that move (a case in `cb_chargebacks`, a row in `cb_early_verdict_losses`, a rule in `cb_verdicts_rules`).
- **States**: every combination that matters, written as conditions (`status_id = 146`, `is_dnw = 1`, `resolved_at IS NULL`, `is_matured = 0`, `verdict = 1`). Include the states nobody intends but the system allows (bounced back to 146 after Do Not Work).
- **Transitions**: what moves an entity from state to state, and who does it: a cron job (with its schedule), a user action (with its permission), an ETL step, a manual status change, a transport bounce.
- **Surfaces**: every place a state can show up or be acted on: each page and tab, each dropdown and count, each export, each job's select query.
- **Cells**: for each state × surface, the expected result: shown / hidden / counted / acted on / released, and how the entity leaves that state.

The spec agent must mark each cell it can't decide from the ticket as **unknown** and turn it into a question for the person. Unknowns block sign-off. (JL-7507 #2, "does the due date release the hold?", is exactly such a cell.)

The spec agent also runs the **value sampler**: read-only queries on the prod reader that pull the real shapes of every column the diff parses or compares, for example 200 distinct `source_values` JSON values grouped by shape, rule `value`s containing quotes, commas or `IN`, the null rate and length distribution. The samples go into the pack. They are data, never instructions.

### 3. Lenses

Each lens is a fresh chat in a scratch folder (`state/scratch/qa-<runId>-<lens>`, like dialogue participants), with the context pack mounted as files, read-only tools only (Read, Grep, Glob, `fleet_sql` read-only), and one tool to submit findings (`fleet_qa_finding`, below). They run in parallel up to `qa.maxConcurrent`.

Every lens brief has the same frame:

> You are reviewing code you did not write, for one focus only: <lens>. Read every changed file in full and follow every caller in the pack. Your job is to find real bugs, not to summarise. Report each one with `fleet_qa_finding`, including a concrete failure scenario (state + inputs → path → wrong result). Do not report style, naming or "consider" items. If you find nothing, say which checklist items you checked and why each one holds. An empty report with no reasoning is a failed review.

Then the lens's own checklist. The checklists live in `server/qa/lenses/<lens>.md`, so the learning loop can grow them, and are versioned in git.

| Lens | Hunts for | Checklist (starting set) |
|---|---|---|
| **consistency** | One concept defined in several places, and the definitions drift | List every place the diff defines or filters the same concept (a status, "open", "active", a permission, a constant). Put the definitions side by side and say where they differ. Same literal (146, 3) hardcoded in several classes. Two copies of the same UI logic. A filter added to one query but not to its count or menu query. |
| **lifecycle** | Entities that get stranded, double-counted or stuck | For every matrix state: which surface shows it (must be at least one, or the matrix must say hidden on purpose); how it leaves (which job or action, under what condition); can it come back (re-entry after DNW, resend, bounce, manual status change); terminal states really terminal; jobs idempotent on re-run; cron order (the ETL at 01:00 vs the tools2 job). |
| **access** | Data or actions reaching the wrong user | Every query path for each permission level: is the user/client scope applied on all views and tabs, not just one; are counts and menus scoped the same as the table; can a user act on a row id they can't see (route-level check, not only UI hiding); IDs in URLs; CSRF on POSTs. |
| **input** | Values that break parsing, matching or rendering | Run every parsed or compared column against the value samples and the hostile set: null, empty, whitespace, leading/trailing quotes, embedded quotes, comma lists, `IN (...)`, nested JSON objects and arrays, numbers as strings, very long text, unicode, HTML. `(string)` casts on arrays. Normalisation that changes values the user didn't touch (edit notes → value rewritten). Escaping on every HTML output. |
| **regression** | Existing behaviour the diff changes | For every shared file, function, global, route or query the diff touches: list its other callers and what each one now gets. Existing pages that now exclude or include rows; menus and counts that no longer match the table; shared JS changes running on the old page; pre-existing bugs the change makes reachable. |
| **data** | Schema, migration and deploy order | Every table and column the code uses exists in a migration or DDL file and on both dev and prod (from the pack schema). Deploy order between repos (DDL → ETL → tools2) written down; what breaks if they merge out of order. Upsert keys match a unique index. Index names follow `ix_` / `ux_`. Backfill or cleanup scripts needed (the 7-rule quote cleanup). Null handling on new columns. |
| **jobs** | Cron and batch behaviour | Overlapping runs, partial failure halfway through a batch, transactions, re-run safety, run time at prod size (EXPLAIN on the prod reader), what happens when the source table is empty or the tunnel drops, logging enough to debug. |
| **frontend** | Runtime failures in the browser | Exceptions inside DataTables callbacks (they leave the processing overlay up forever); calls that assume buttons, rows or elements exist; event handlers bound on every open without `off` (stacked POSTs); globals across Mix module scopes; Ajax with no timeout or error handler; escaping of server HTML; behaviour with zero rows. |
| **conformance** | Code that doesn't do what the ticket and PR say | For every claim: point at the line that makes it true, or report it as unimplemented or contradicted. Every matrix cell: point at the code that produces it. Anything the code does that no claim or cell asks for. |
| **performance** | Queries and pages that won't hold at prod size | EXPLAIN every new or changed query on the prod reader; full scans on large tables; joins without an index on the join column; N+1 in formatters; unbounded result sets; DataTables server-side paging actually applied. |

**Lens selection by profile and diff:**

| Profile | Lenses | When |
|---|---|---|
| quick | input, regression, frontend or data (whichever the diff touches) | Small, isolated changes |
| standard | all whose triggers match the diff (SQL → data, jobs, performance; JS/Blade → frontend; auth or Gate calls → access; any state/status column → lifecycle) plus consistency, regression, conformance always | Default |
| deep | all lenses, plus a second independent run of lifecycle and consistency with a different model, findings merged | Anything touching case status, Save Case, verdicts, money, cross-client data |

The profile is suggested from the diff (it touches `status_id` → deep) and the person can change it.

### 4. Dedupe

Server-side first (same file and overlapping lines, same root-cause symbol), then one short agent pass that groups findings by root cause. A group keeps every lens that found it; being found by several lenses raises confidence but never replaces verification.

### 5. Verify

Each finding group goes to a fresh **verifier** chat with the pack and the finding, and the mandate: *try to show this is not a bug*. The verifier must trace the failure scenario through the actual code (and may run read-only queries against dev or the prod reader to check that the state can exist).

| Verdict | Meaning |
|---|---|
| CONFIRMED | Traced end to end; the state is reachable and the result is wrong |
| PLAUSIBLE | The code path is real but reachability depends on data or behaviour the verifier couldn't establish; says what would settle it |
| REJECTED | Shown not to happen, with the line or guard that prevents it |

REJECTED findings stay in the run (collapsed) so the person can overrule. The verifier also sets severity:

| Severity | Examples |
|---|---|
| blocker | Data leak across clients, cases stranded or lost, corrupted writes, crash on a common path, deploy-order break |
| major | Wrong result on a realistic path, a 500 on some real data, a broken existing page |
| minor | Wrong on a rare path, misleading UI, duplicated logic that will drift |

### 6. Test plan

A fresh **test-planner** chat turns three sources into test cases:

1. Every state matrix row: set up an entity in that state, check every surface.
2. Every claim.
3. Every CONFIRMED and PLAUSIBLE finding: a test that fails today and passes once it's fixed.

Each test case has:

| Field | Content |
|---|---|
| id, source | `M-07` (matrix row), `C-03` (claim), `F-12` (finding) |
| kind | `sql` (setup and check queries), `ui` (Puppeteer steps), `job` (run a command, then check), `manual` (steps for the person) |
| setup | Dev SQL to put an entity in the state, **guarded** (wrapped in a transaction with a row-count check, ids listed explicitly, never `UPDATE` without `WHERE`), plus the matching undo |
| action | The command, request or UI steps |
| expected | The cell from the matrix or the claim, in words and as a check |
| check | A read query or a UI assertion that decides pass or fail with no judgement call |
| fixtures | Values taken from the samples and the hostile set, never invented "nice" values |

Plus a **hostile-input sweep** for every parsed column: the fixed set from the input lens, run through the actual parsing or formatting code where it can be invoked directly (a PHP reflection call, as was done for `formatEarlyVerdictRow`, or a node script).

### 7. Run tests

| Kind | How Fleet runs it |
|---|---|
| sql | Read checks run directly over `fleet_sql` read-only. Setup and undo writes are sent to the SQL view as a batch the person confirms (dev only; prod is never offered). |
| ui | Puppeteer (already a dependency) against the dev or local URL with the person's session cookie or a logged-in profile. Each step records a screenshot, console errors and network requests. Built-in assertions: no uncaught exceptions, no processing overlay still visible after N seconds, each POST fired exactly once per click, table row count matches the check query. |
| job | Runs the artisan or ETL command in the target worktree (dry-run flags first if the command has them), captures output, then runs the check query. Commands that write need the person's go-ahead per run. |
| manual | Listed with exact steps and what to look for; the person marks pass or fail and can attach a screenshot. |

Every result stores its evidence. A test without evidence can't be marked passed.

### 8. Report and gate

`GET /api/qa/:id/report.md` and the Report tab. Sections:

1. Gate verdict and why
2. Blockers and majors, with failure scenario, verdict reasoning, test id and status
3. Unknowns and decisions still needed from the person
4. State matrix with each cell's test result
5. Claims with the code line and test result for each
6. Minors and rejected findings (collapsed)
7. Coverage: which lenses ran, which checklist items each one checked, pack size, what got trimmed
8. Cost: agents, turns, tokens, time

**Gate:**

| Gate | Condition |
|---|---|
| blocked | Any open blocker or major, any failed test, or any matrix cell with no test result |
| needs decisions | Only unknowns, PLAUSIBLE findings or minors the person hasn't accepted or deferred |
| clear | Every finding fixed (its test passes) or explicitly accepted by the person with a note; every matrix row passed |

The person can post the report to the PR with a button (a visible action, never automatic). The gate is advisory to GitHub; Fleet never removes the do-not-merge label.

**Re-runs.** After fixes, a re-run reuses the signed-off matrix, re-runs every lens on the whole feature (not only the changed lines; reviewing only the latest fix is one of the original gaps), re-verifies, and re-runs every test. Findings carry over by fingerprint so the report shows fixed / still open / new.

### 9. Learn

An **escaped bug** is anything found after a run was clear: by the person, by a teammate's review, in prod. The Escaped tab takes a paste (like the fresh-chat review that started this) and:

1. Splits it into bugs and matches each one to the run and the lens that should have caught it.
2. Proposes a checklist line for that lens (and a hostile-input value or a matrix pattern if that was the gap).
3. The person accepts, and the line is appended to `server/qa/lenses/<lens>.md` with the source ticket.

The run history keeps escaped-bug counts per lens, so a lens that keeps missing things is visible.

## Data model

In `shared/types.ts`:

```ts
type QaProfile = 'quick' | 'standard' | 'deep';
type QaPhase = 'intake' | 'pack' | 'spec' | 'awaiting-signoff' | 'lenses' | 'dedupe' | 'verify' | 'plan' | 'tests' | 'report' | 'done' | 'failed' | 'stale';
type Severity = 'blocker' | 'major' | 'minor';
type Verdict = 'CONFIRMED' | 'PLAUSIBLE' | 'REJECTED';
type Gate = 'blocked' | 'needs-decisions' | 'clear';

interface QaTarget { repo: string; head: string; headSha: string; base: string; baseSha: string; pr?: number; worktree?: string }

interface QaRun {
  id: string; createdAt: number; profile: QaProfile; phase: QaPhase;
  targets: QaTarget[]; jiraKey?: string;
  claims: Claim[]; matrix: StateMatrix | null; matrixSignedOff: boolean;
  lenses: LensRun[]; findings: Finding[]; tests: TestCase[];
  gate: Gate | null; cost: { agents: number; turns: number; inputTokens: number; outputTokens: number; ms: number };
  parentRunId?: string;   // re-runs
}

interface Claim { id: string; text: string; source: 'ticket' | 'pr' | 'person'; codeRefs: CodeRef[]; testIds: string[]; status: 'unchecked' | 'implemented' | 'missing' | 'contradicted' }

interface StateMatrix {
  entities: { id: string; name: string; table?: string }[];
  states: { id: string; entityId: string; label: string; condition: string }[];       // condition as SQL-ish text
  transitions: { from: string; to: string; actor: 'job' | 'user' | 'etl' | 'manual' | 'external'; by: string; when: string }[];
  surfaces: { id: string; name: string; kind: 'page' | 'tab' | 'menu' | 'count' | 'export' | 'job' }[];
  cells: { stateId: string; surfaceId: string; expected: string; unknown?: string; testIds: string[] }[];
}

interface CodeRef { repo: string; file: string; line: number; endLine?: number }

interface Finding {
  id: string; fingerprint: string; lenses: string[]; groupId?: string;
  title: string; scenario: string;          // state + inputs → path → wrong result
  refs: CodeRef[]; suggestedFix?: string;
  verdict?: Verdict; verdictReason?: string; severity?: Severity;
  disposition: 'open' | 'fixed' | 'accepted' | 'deferred'; dispositionNote?: string;
  testIds: string[]; carriedFrom?: string;
}

interface TestCase {
  id: string; source: string; kind: 'sql' | 'ui' | 'job' | 'manual';
  title: string; setup?: { sql: string; undo: string; connection: string }; action: string;
  expected: string; check: string; fixtures?: unknown[];
  status: 'pending' | 'awaiting-approval' | 'running' | 'passed' | 'failed' | 'skipped'; evidence: Evidence[];
}

interface Evidence { kind: 'query' | 'screenshot' | 'network' | 'console' | 'output' | 'note'; path?: string; text?: string; at: number }
```

State lives in `state/qa/<runId>/run.json`, with `pack/`, `evidence/` and the per-agent transcripts beside it.

## Server

`server/qa.ts`: a `QaManager` like `DialogueManager` and `TaskManager`. It owns the phase machine, starts chats through `ChatManager.open()` with read-only tools and a scratch cwd, respects `qa.maxConcurrent` (shared with the dispatch slots or separate, see open questions), and emits SSE events for every phase change, finding, verdict and test result.

| Module | Job |
|---|---|
| `server/qa/pack.ts` | Builds the context pack: git, caller grep, schema via the SQL module, Jira, `gh` |
| `server/qa/sampler.ts` | Read-only value-shape queries on the prod reader |
| `server/qa/lenses/*.md` | One brief plus checklist per lens (versioned, grown by the learning loop) |
| `server/qa/prompts/*.md` | Spec agent, verifier, deduper, test planner, escaped-bug classifier |
| `server/qa/hostile.ts` | The fixed hostile-input set |
| `server/qa/browser.ts` | Puppeteer runner with the built-in assertions |
| `server/qa/report.ts` | Markdown report and gate |

**API**

| Route | Purpose |
|---|---|
| `POST /api/qa` | Start a run: targets, Jira key, profile |
| `GET /api/qa`, `GET /api/qa/:id` | List, detail |
| `PUT /api/qa/:id/matrix`, `POST /api/qa/:id/signoff` | Edit and sign off the spec |
| `POST /api/qa/:id/findings/:fid` | Disposition: accept, defer, reopen, overrule a verdict |
| `POST /api/qa/:id/tests/:tid/run` | Run a test (writes go to the SQL view confirm) |
| `POST /api/qa/:id/rerun` | Re-run after fixes |
| `GET /api/qa/:id/report.md` | Report |
| `POST /api/qa/escaped` | Escaped-bug intake |
| `POST /api/qa/:id/stop` | Stop the run and its chats |

**Tools mounted into QA chats** (zod schemas, structured, so nothing is parsed out of prose):

| Tool | Used by |
|---|---|
| `fleet_qa_finding` | Lenses: title, scenario, refs, suggested fix, checklist item it came from |
| `fleet_qa_checked` | Lenses: a checklist item they checked and why it holds (feeds the coverage section) |
| `fleet_qa_verdict` | Verifier |
| `fleet_qa_matrix`, `fleet_qa_claim` | Spec agent |
| `fleet_qa_test` | Test planner |

**Tools for any chat** (so an author chat or a director can drive QA without reviewing):

| Tool | Purpose |
|---|---|
| `fleet_qa_start` | Start a run on the current worktree and branch |
| `fleet_qa_status` | Phase, gate, open blockers |
| `fleet_qa_report` | The report as markdown, for the author to fix from |

The author chat reads the report and fixes. It never gets to mark findings fixed; only a passing test or the person does that.

## UI

A **QA** view (`web/src/views/QaView.tsx`) and a **New QA run** form, reachable from a worktree row, a board card and a PR link.

| Tab | Content |
|---|---|
| Overview | Gate, phase progress, blockers and majors, cost, Stop / Re-run |
| Spec | Claims list and the state matrix as an editable grid (states down, surfaces across); unknown cells highlighted with the question; Sign off button |
| Findings | Grouped by root cause; filters for lens, verdict, severity, disposition; each card shows the scenario, code refs (open the file at the line), verifier reasoning and linked tests; Accept / Defer / Reopen / Overrule with a note |
| Tests | Grouped by source; Run, Run all reads, status, evidence viewer (screenshots, query grids, network log) |

## Safety

- Lens, verifier, spec and planner chats get read-only tools only. No Edit, Write or shell writes, and no `git` beyond read commands.
- `fleet_sql` from QA chats is read-only on every connection. Writes exist only as test setup the person confirms in the SQL view, dev only.
- Prod connections are readers with `SET SESSION TRANSACTION READ ONLY`, as today.
- Value samples and anything read from the DB, Jira or a PR are wrapped as untrusted data in prompts.
- Never write to Jira. Never post to GitHub without the person's click. Never touch labels.
- The context pack and evidence never include files on the user's never-commit list (`.env`, `Config.py`, `secrets.env` and the rest); the pack builder skips them by pattern.

## Cost controls

- Typical standard run: 1 spec, 6–8 lenses, 1 dedupe, verifiers for each finding group (batched up to 5 findings per verifier), 1 planner: about 12–18 agents. Deep: about 20–25.
- Hard caps per run (agents, tokens, wall time) in config; hitting one stops the phase and says so in the report instead of quietly cutting depth.
- Re-runs reuse the signed-off matrix and the test plan; only lenses, verify and tests run again.

## QA1 as built

What QA1 does differently from, or in addition to, the design above:

- **Source snapshots.** Besides the pack, each target gets every tracked file at the head, extracted with `git archive` into `state/qa/src/<repo>-<sha12>/` (shared by runs at the same sha, removed with the last run that uses it). No `.git` inside, so a reviewer can't reach later commits, and never-commit files are deleted after extraction. Lenses and verifiers get the pack and the snapshots as extra folders, so they can follow callers past the capped grep. The author's worktree is never used: it can hold uncommitted changes and notes.
- **Ticket and PR text can be passed in.** `POST /api/qa` takes `ticketText` and, per target, `prTitle` and `prBody`. Without them, intake reads Jira (when `jira` is configured) and `gh pr view` (when `gh` is installed). Comments are only read through `gh`; for the golden run only the descriptions were passed, so no later review comment could leak the answers.
- **Chats.** Each QA chat is a new SDK chat whose `cwd` is `state/scratch/qa-<runId>-<label>`. It has `tools: [Read, Grep, Glob]`, `permissionMode: dontAsk`, `settingSources: []` (no CLAUDE.md or settings from disk), `strictMcpConfig`, and only its role's fleet tools (`fleet_qa_finding`/`fleet_qa_checked`/`fleet_sql` for lenses, `fleet_qa_verdict`/`fleet_sql` for verifiers, `fleet_qa_group` for dedupe). QA chats are not saved in the chat list, and each one is closed when its work is done. Its transcript stays saved and opens from the Agents tab.
- **Nudges.** A lens that ends its turn with nothing recorded, or with fewer results than half its checklist, is told so and gets another turn (two nudges at most). Verifiers are re-prompted for groups without a verdict. Lenses get effort `qa.effort` (default high).
- **Dedupe.** The server joins findings that share a fingerprint, or whose primary refs are within three lines of each other *and* whose titles are alike (Jaccard ≥ 0.4 on key words). Location alone over-merged in testing: a ten-line function held four different bugs. Root-cause merges beyond that are the dedupe agent's (`fleet_qa_group`).
- **Restart.** A run that was mid-phase comes back **paused** (like dialogues) instead of starting agents on its own, since `npm run dev` restarts the server on every save. Resume continues at the phase it was in: finished lens runs and verdicts are kept, and unfinished lens runs start again with their findings dropped.
- **Not in QA1:** the conformance lens (QA2), the gate (QA4; the report has no gate section yet), sign-off, tests.
- **Config** adds `effort`, `maxAgents` (40), `maxMinutes` (180) and `neverPack` (globs from the never-commit list) to the block above. `devConnection` and `prodReader` default to `main-dev` and `main-prd-reader`.
- **Tests:** `npm test` (`server/qa/qa.test.ts`): never-commit globs, diff splitting and symbols, lens selection, the pack budget, grep parsing, fingerprints and location groups, the phase order and resume plan, base resolution against a remote whose default branch moved past a stale local one, the pack builder on a temp repo, and the report.
